# 6 层改造草案 / Six-Layer Refactor Draft

## 目标 / Goal

在不推翻现有可运行链路的前提下，将当前仓库逐步演进为“采集 → 整理 → 策划 → 创作 → 包装 → 分发”的六层结构，降低模块耦合，提升 Claude 与 Codex 并行协作效率。

Without discarding the existing working pipeline, evolve the repository into a six-layer structure of “Collect → Normalize → Plan → Create → Package → Distribute,” reducing module coupling and improving parallel collaboration efficiency between Claude and Codex.

## 改造原则 / Refactor Principles

- 先定义契约，再迁移代码。
- 先拆边界最混乱的层，再扩展新能力。
- 先保证现有 CLI 和流水线不回归，再逐步迁移目录结构。
- 新层级能复用旧实现时优先包裹，不做无意义重写。

- Define contracts first, then migrate code.
- Split the most entangled boundaries before adding new capabilities.
- Keep the current CLI and pipeline stable before moving directory structures.
- Prefer wrapping and reusing existing implementations over unnecessary rewrites.

## 当前仓库问题 / Current Repository Issues

### 问题 1：采集层过重 / Problem 1: The collect layer is too heavy

当前 `collector` 同时承担采集、清洗、去重、策划前处理、Notion 输出等职责，边界偏模糊。

The current `collector` handles collection, cleaning, deduplication, pre-planning processing, and Notion output all at once, so its boundaries are too blurry.

### 问题 2：包装层缺失 / Problem 2: The packaging layer is missing

现在平台格式转换逻辑主要散落在 `publisher` 里，导致发布器既要适配平台，又要负责内容格式化。

Platform-specific formatting is currently scattered inside `publisher`, so publishers must both adapt to platforms and format content.

### 问题 3：中间产物不够正式 / Problem 3: Intermediate artifacts are not formal enough

现有 `pool.json`、Markdown 草稿和平台发布输入缺少统一建模，重跑与回放成本偏高。

Current pool JSON, Markdown drafts, and platform publish inputs are not modeled uniformly, which raises the cost of reruns and replay.

## 建议的改造顺序 / Recommended Refactor Order

### 第一步：先把契约定死 / Step 1: Lock the contracts first

产出：
- `docs/内容流水线数据契约.md`
- `TopicCandidate`、`DraftPackage`、`PublishPackage` 的字段定义

Outputs:
- `docs/内容流水线数据契约.md`
- Field definitions for `TopicCandidate`, `DraftPackage`, and `PublishPackage`

### 第二步：拆整理层 / Step 2: Split the normalize layer

动作：
- 把 `dedup.py` 从 `collector` 中迁出或封装
- 把清洗、翻译、正文补齐逻辑集中到 `normalizer`
- 让 `search.py` 只负责编排，不再承载全部处理逻辑

Actions:
- Move or wrap `dedup.py` out of `collector`
- Centralize cleaning, translation, and content enrichment into `normalizer`
- Make `search.py` orchestrate instead of containing all processing logic

### 第三步：补包装层 / Step 3: Add the packaging layer

动作：
- 抽离 Markdown 转平台格式逻辑
- 让 publisher 改成“吃发布包”，而不是“自己加工草稿”
- 为每个平台建立独立 `packager`

Actions:
- Extract Markdown-to-platform formatting logic
- Make publishers consume a publish package instead of transforming drafts themselves
- Create one `packager` per platform

### 第四步：统一中间产物 / Step 4: Standardize intermediate artifacts

建议目录：

Recommended directories:

```text
content/
├── raw/          # 原始采集结果
├── normalized/   # 清洗去重后的素材池
├── topics/       # 策划结果
├── drafts/       # 创作层草稿
├── packages/     # 平台发布包
└── published/    # 发布归档
```

### 第五步：最后再扩展多媒体 / Step 5: Expand multimedia last

动作：
- 增加视频脚本输出
- 增加语音稿输出
- 增加短视频或图文视频包装

Actions:
- Add video-script outputs
- Add voice-script outputs
- Add short-video or motion-graphic packaging

## 对当前代码的直接建议 / Immediate Code Recommendations

1. 保留 `src/collector/sources/` 不动，避免一次性重写采集器。
2. 新建 `src/normalizer/`，先做薄封装，再逐步迁移逻辑。
3. 新建 `src/packager/`，先承接公众号和知乎两个平台。
4. 让 `src/pipeline/main.py` 的阶段命名逐步对齐六层术语。

1. Keep `src/collector/sources/` intact to avoid rewriting collectors in one shot.
2. Create `src/normalizer/` as a thin wrapper first, then migrate logic gradually.
3. Create `src/packager/` and start with WeChat and Zhihu.
4. Gradually align stage names in `src/pipeline/main.py` with the six-layer terminology.

## 协作建议 / Collaboration Guidance

建议分工：
- Claude：维护架构文档、数据契约、流程说明、迁移清单
- Codex：落代码骨架、迁移模块边界、补测试、调整 CLI

Recommended split:
- Claude: maintain architecture docs, data contracts, process docs, and migration checklists
- Codex: implement scaffolding, migrate module boundaries, add tests, and adjust the CLI

推荐顺序：
- 先文档
- 后骨架
- 再迁移逻辑
- 最后做完整回归

Recommended sequence:
- Documents first
- Scaffolding second
- Logic migration third
- Full regression last

- `TopicCandidate`、`DraftPackage`、`PublishPackage` 有明确 schema。
- `publisher` 不再承担主要格式转换职责。
- `collector` 不再直接承载所有整理逻辑。

- The six-layer terminology is aligned across docs, directories, and pipeline stages.
- `TopicCandidate`, `DraftPackage`, and `PublishPackage` have explicit schemas.
- `publisher` no longer owns most formatting logic.
- `collector` no longer carries all normalize responsibilities directly.
